# Decision history

Updated 2026-11-04. The [design](design.md) and
[PostgreSQL data core](postgresql-data-core.md) define the current design.
This record explains its relationship to earlier decisions; it does not add
requirements or claim that the design has been implemented.

The original [ADRs][adrs], [research][research] and [reviews][reviews] are retained
at commit `1cb968837e55df88db7a17d9ad3f3975e961836f`. They include alternatives and
intermediate proposals. Their implementation mechanisms are not additional
systems to build. Unresolved changes to their guarantees remain explicit in
the [design's open decisions](design.md#unanswered-policy-questions); moving to PostgreSQL does not silently
waive those guarantees.

## Architecture transition

The earlier design used Git commits as accepted registry revisions and immutable
GitHub releases for artifact distribution. The current direction uses one
self-hosted service and PostgreSQL, with a shared checker and authenticated
retrieval of retained artifacts. Hosted registry subscriptions are excluded.

PostgreSQL provides transactional publication, relational integrity and indexed
accepted-request lookup in one store. This removes Git object construction,
conditional remote-ref updates, acceptance-history traversal and mandatory release
uploads from the registry. Source Git revisions remain provenance; they do not
identify accepted registry revisions or generated bytes.

This is a complexity trade-off, not a measured availability improvement. The
operator assumes responsibility for the service, database capacity, durable
storage, backups and restoration. Direct retrieval also makes cold-start
availability depend on the registry or a verified copy of the selected artifact.

No queue or durable pending-work inventory is included: publication is requested
explicitly, accepted requests are recoverable, and callers own retries after
terminal rejection. No second artifact store is required to retain the outputs
atomically with acceptance. Adding either would introduce another persistence
and recovery lifecycle without a demonstrated requirement. Workload or availability
evidence may justify revisiting these choices.

The [independent assessment][assessment] records the alternatives and failure
analysis. Its proposed reductions in source-order, rejection-freshness and control
admission guarantees were not all adopted by selecting PostgreSQL.

## ADR disposition

**Retained** preserves the decision. **Amended** preserves its identified contract
with revised scope or mechanics. **Historical** is no longer a current design
instruction. **Unresolved in part** separates retained guarantees from policy
changes that still require a decision.

| ADR | Disposition | Current interpretation |
| --- | --- | --- |
| [0001 — Compatibility exceptions][0001] | Retained | Source-repository controls own exceptions; accepted breaking changes retain failing compatibility results. |
| [0002 — No environment model][0002] | Retained | Deployment environments and promotion are outside the domain model. |
| [0003 — Bounded static assurance][0003] | Amended | Static schema checks remain bounded; empty registry revisions have no composed artifact and no successful composition result. |
| [0004 — Explicit activation][0004] | Retained | Gateway deployment selects an artifact explicitly. Registry acceptance does not activate it. |
| [0005 — Graph-directory input][0005] | Amended | Complete graph inputs remain the checker boundary. One registry repository per graph is historical storage topology. |
| [0006 — Release artifacts][0006] | Historical | ADR 0010 first replaced post-acceptance generation; PostgreSQL now replaces mandatory GitHub release distribution. |
| [0007 — Source-PR checks][0007] | Retained | Schema assessment belongs on source PRs before merge. |
| [0008 — Source-owned approval][0008] | Retained | Source PRs own approval; scoped publication avoids a second registry-PR lifecycle. Maintainers retain control of routing, policy and ownership. |
| [0009 — Snapshot checks and conditional updates][0009] | Retained | Checks identify their baseline; publication retries unrelated changes while preserving each participant's original condition. |
| [0010 — Retained outputs][0010] | Amended | Inputs, outputs and receipts are retained atomically in PostgreSQL, without automatic expiry. Git commits and release uploads are replaced. |
| [0011 — Retry and receipt semantics][0011] | Unresolved in part | Accepted-request recovery and caller-owned retries remain. Stronger rejection-freshness, rejected-key and generation-consistency rules require reconciliation. |
| [0012 — Source-history ordering][0012] | Unresolved in part | Batch integrity and distinct publication identities remain. Optimistic concurrency alone does not replace the source-ancestry guarantee. |
| [0013 — Maintainer controls][0013] | Unresolved in part | Scoped maintainer authority and complete artifact inputs remain. Configuration admission, revocation lifetime and checker-upgrade semantics require reconciliation. |
| [0014 — Actions OIDC][0014] | Amended | Scoped CI authentication and provenance limits remain. A GitHub App may report checks; PostgreSQL publication replaces Git registry writes. |

## Subsequent data-core decisions

The data-core discussion established per-subgraph optimistic concurrency with
automatic recomposition after unrelated publications. An addition requires
current absence. A never-accepted delayed addition may therefore recreate a name
after another request adds and removes it; this consequence was accepted without
adding deletion versions or a graph-wide caller precondition.

Graphs may contain zero subgraphs initially or after removal. The tested Apollo
libraries do not compose an executable empty graph, so these revisions retain
their identity and history with absent artifacts. Historical artifacts remain
available for explicit deployment selection. The data core records the exact
experiment versions and verification limits.
