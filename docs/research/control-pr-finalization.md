# Maintainer control PR finalization on GitHub

Research date: 2026-11-01. This note supports the control-change decision in
[the design discussion](../design.md#current-decision-frontier) and the complete
accepted snapshot required by
[ADR 0010](../adr/0010-retain-validated-outputs-with-acceptance.md). Current
GitHub primary documentation was read. No hosted mutation, authenticated
workflow, branch-protection experiment, or source implementation was performed.
The options below do not choose new approval authority or change accepted
contracts.

The governing direction is separate maintainer PRs for controls, admission under
existing accepted controls, and an explicit authenticated request that applies
the exact approved control change through the trusted finalizer. The finalizer
reconstructs against the latest graph, generates matching outputs, and commits
conditionally. The earlier integration candidate in this note lets a calling CI
workflow own requests and retries, without service webhook subscriptions or a
PR inventory. The user subsequently proposed Selvedge-owned storage merging;
[that comparison](storage-pr-events.md) now informs the open Q27 decision.
Neither integration has been accepted.

## Findings that constrain the workflow

### A PR-head condition is not an accepted-branch condition

REST PR merge accepts `sha` for the expected PR head; GraphQL
`mergePullRequest` has the equivalent `expectedHeadOid`. Neither documented
input accepts an expected target-branch head or a caller-prepared tree. Reading
the target before requesting a native merge therefore does not establish an
atomic equality condition on that target.
[REST merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request),
[GraphQL merge input](https://docs.github.com/en/graphql/reference/pulls#mergepullrequestinput).

Current REST documentation also describes asynchronous PR merging. Its head
condition still names the PR head. An accepted asynchronous request or an
enqueued result is not proof of a completed merge, and its result record expires
24 hours after its most recent update. It cannot replace Selvedge's retained
publication receipt.
[Asynchronous merge and result](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously).

GraphQL `updateRefs` supports atomic updates within one repository and a
`beforeOid` condition for each ref. It can install a prepared commit only while
the accepted branch still points to the validated head. Its input does not
include PR approval state. `force` permits a non-fast-forward update; that is
separate from the old-value condition. REST update-reference instead exposes
`sha` and `force`, without an expected-old-OID parameter.
[Atomic ref updates](https://docs.github.com/en/graphql/reference/git#updaterefs),
[RefUpdate input](https://docs.github.com/en/graphql/reference/git#refupdate),
[REST reference update](https://docs.github.com/en/rest/git/refs#update-a-reference).

**Design inference:** native PR merging and conditional acceptance solve
different parts of this problem. A read of PR approval followed by `updateRefs`
is not a documented transaction over both approval and acceptance. An explicit
externally authorized publication request can bind exact inputs without making
the service reconstruct GitHub's approval policy.

### Retaining a PR parent does not prove review or contents

The Git commit API accepts a tree OID and a list of parent OIDs, including
multiple parents. A finalizer can therefore construct a commit with accepted
head `H` as first parent and reviewed PR head `P` as second parent, while using
its generated complete-snapshot tree `T`. Those fields do not require GitHub to
compute the ordinary merge tree.
[Commit creation](https://docs.github.com/en/rest/git/commits#create-a-commit).

GitHub documents indirect PR merges when the original head commits become
reachable from the base through another route. It explicitly warns that the PR
can be marked merged even when its protection requirements were unsatisfied.
The documentation gives another PR and a push to the default branch as examples.
[Indirect merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges).

**Design inference:** parent `P` provides an ancestry link, not proof that `T`
contains the reviewed changes, that generated bytes match the inputs, or that
approval rules passed. Copying equivalent file bytes or creating rewritten
commits does not preserve the original head's ancestry. Conversely, retaining
`P` can preserve its ancestry even when a constructed tree omits some of its
changes. The finalizer must establish exact content independently.

**Untested host behavior:** recognition timing, the resulting PR
`merge_commit_sha`, event delivery, and recognition for the chosen non-default
accepted branch after `updateRefs` were not exercised. Current documentation
does not establish a synchronous PR-state update as part of that mutation.
Do not make acceptance correctness depend on the PR badge changing promptly.

### Branch protection can reject the constructed tree

With stale-approval dismissal or approval of the latest reviewable push enabled,
GitHub documents that a manually pushed merge fails unless its contents match
GitHub's expected PR merge. A linear-history rule also rejects merge commits.
Force-push permission does not disable other protection rules.
[Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging),
[Linear history and force pushes](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-linear-history).

Rulesets can restrict updates to bypass actors and require verified signatures.
A ruleset bypass restricted to PRs does not grant direct-push permission.
The mutation's existence is not evidence that the selected credential may use
it against the intended protected branch.
[Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets),
[Bypass configuration](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#creating-a-branch-or-tag-ruleset).

**Design inference:** adding fresh generated outputs and a receipt after review
will generally produce a tree different from the ordinary merge of a control-only
PR. Keeping the PR as a second parent does not make that tree acceptable to
native review enforcement. A compatible externally configured writer path, or a
workflow that first puts the exact complete candidate into the PR, is necessary.
No branch-rule changes or bypass grants are selected by this research.

## Option A: native review-branch merge, then explicit publication

In maintainer terms, this is one PR followed by its publication job. For example,
a PR selects a new composer version. Merging records the reviewed control
change. CI then asks Selvedge to use it with the latest accepted subgraph inputs,
compose, and retain the complete new snapshot. If that fails, the PR is still
merged but the registry continues using its previous accepted controls and
outputs. No second human approval or mirrored schema PR is introduced.

The two branches represent those two stages: reviewed maintained inputs, and
complete snapshots accepted by the finalizer. Q27 asks whether merge may precede
application. The alternative is to include generated
output in the maintainer PR and keep it current until native merge, accepting
the resulting regeneration and review cost. Branch names themselves are an
implementation choice.

A dedicated control-review branch can receive maintainer PRs through GitHub's
normal merge controls. It records reviewed control changes, not accepted graph
snapshots. Trusted CI then explicitly requests publication of one identified
change. The accepted registry branch moves only after the finalizer retains the
complete matching snapshot and receipt.

The proposed sequence is:

1. A maintainer PR is reviewed and merged into the control-review branch under
   externally configured repository rules.
2. Trusted CI identifies the immutable merged revision and exact control delta,
   then submits an authenticated publication intent. It does not submit whatever
   the branch happens to contain when a delayed run starts.
3. The finalizer verifies the request's allowed scope and input binding against
   the existing accepted controls, loads accepted head `H`, and applies that
   delta while preserving the current graph inputs.
4. It evaluates the proposed controls, retains generated outputs and the
   receipt, and conditionally accepts the resulting commit against `H`.
   Independent graph advancement causes reconstruction and recomposition.
5. CI reports acceptance, rejection, or an operational failure. Rejected changes
   are not queued by the service. Explicit retry uses the same intent identity
   to recover any original acceptance before attempting new work.

These steps are a design proposal using the accepted contracts, not an observed
GitHub integration. Their benefit is that native PR approval and merge occur
before the separate generated snapshot is accepted. No service-owned approval
policy is required.

The cost is a visible intermediate state: a control PR may be merged while the
registry still uses earlier controls. Fresh composition can reject it or the
publishing pipeline can fail. A merged control-review branch must not be exposed
as an approved graph configuration or silently consumed by schema publishers.
The acceptance receipt resolves whether its controls took effect.

GitHub Actions can run on pushes to selected branches; its push SHA identifies
the tip pushed by the event. A push made with the workflow's `GITHUB_TOKEN` does
not trigger another push workflow, so automatic merging and publishing must not
assume that chain always runs. An explicit invocation in the trusted workflow,
or an explicit dispatch, can avoid that dependency.
[Push events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push),
[GITHUB_TOKEN event behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs).

**Admission caveat:** GitHub uses the PR base branch's `CODEOWNERS` file. Thus a
review branch that has advanced beyond accepted controls can also have different
review ownership. That does not automatically implement the agreed rule that
existing accepted controls govern admission. External repository governance and
the finalizer's accepted control snapshot need an explicit boundary; this note
does not equate GitHub `CODEOWNERS` with Selvedge's subgraph ownership settings.
[Code owners and base branches](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-and-forks).

## Option B: construct the accepted merge with the PR as a parent

An explicit trusted publisher can supply the externally approved `P` and exact
delta. The finalizer computes `T` against current accepted head `H`, creates
commit `(tree=T, parents=[H,P])`, and conditionally moves the accepted ref from
`H`. This preserves the original PR head in ancestry and keeps generated outputs
with acceptance. It also retains all ancestors of `P`, including any proposal
commits that were not themselves complete accepted snapshots.

**Design inference:** this option requires distinguishing accepted commits from
other reachable ancestors. A first-parent acceptance history plus retained
receipts is one possible representation. Treating every reachable commit as an
accepted graph would violate the snapshot guarantee. This is a consequence of
adding the PR parent, not a reason to discard accepted history.

This construction is feasible at the documented object/ref level. It does not
provide native PR approval enforcement for a different generated tree, and
does not turn `updateRefs` into GitHub's merge endpoint. A separately authorized
publisher and compatible accepted-branch rules remain required. The external
publisher must establish the exact authorized change before invoking the
service; a mutable `APPROVED` field followed by a later ref update leaves a race
with review withdrawal or PR edits.

If the requirement is that GitHub must evaluate current PR approval atomically
with the accepted-branch move, this option has not established that guarantee.
The alternative is to prepare the complete generated candidate in the PR and
use native merge enforcement, with additional verification of branch freshness
and resulting candidate identity. That has different review and retry costs and
is not selected here.

## Bind authorization to immutable inputs

GitHub OIDC exposes repository IDs, event/ref identity, run identity, workflow
revision, and, for reusable workflows, `job_workflow_ref` and
`job_workflow_sha`. These support authentication of a specific trusted publishing
workflow. They do not themselves contain a digest of an arbitrary submitted
control delta or assert that all reviews passed.
[OIDC claims](https://docs.github.com/en/actions/reference/security/oidc#oidc-token-claims),
[Reusable-workflow trust](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows).

GitHub documents that ordinary PR workflows use the PR merge revision, while
`pull_request_target` uses default-branch workflow code. Neither event name alone
proves that all executed code came from the accepted control revision.
[Workflow source and execution risks](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

**Design inference:** the trusted workflow/finalizer should derive or verify the
submitted delta from immutable Git objects and bind it to the publication
intent. Record the source repository identity, PR/merged revision, prior control
identity, exact changed paths and before/after contents, and trusted producer
identity. The exact manifest representation is implementation work. Executing
newly merged publication code merely because it is now on the review branch
would not satisfy admission under old accepted controls.

Three changes need different handling:

| Change after review or request preparation | Consequence |
| --- | --- |
| The PR head or submitted control bytes change | The original authorization does not identify the new bytes. Bind the request to an immutable revision/delta; changed input needs its own authorization. |
| Independent subgraph state advances | Reconstruct and recompose against the latest accepted graph, as already agreed. Preserve the approved control delta. |
| Another accepted control update changes the proposal's assumptions | Fresh composition alone cannot decide whether the old approval permits replacement of those controls. Detect the changed predecessor; choose an explicit ordering or renewed-approval contract. |

GitHub's stale-review option tracks the reviewed diff and can dismiss approval
when it changes, including through base changes. Its latest-push approval option
is different: earlier approvals can remain while another authorized reviewer
approves the last reviewable push. Repository settings therefore matter to any
claim about exactly what a review approved.
[Review freshness](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging).

Example of the remaining control-ordering issue: PR A approves a tool change
from version 1 to version 2. Before its publication succeeds, PR B's change from
version 1 to version 3 is accepted. Reapplying A's desired value would replace
version 3 with version 2, despite both individual proposals having been reviewed.
The service can detect that A's expected predecessor no longer matches; whether
A must be reviewed again, or controls must publish in an enforced order, is a
workflow decision. A retry of an already accepted A must instead return A's
original receipt under the accepted recovery contract.

## Decisions still needing the maintainer's choice

The earlier Q27 recommendation refined option A: publish the complete
maintained-control snapshot at the exact
reviewed revision, while preserving source-owned schema/provenance from the
latest accepted graph. Track the applied control-review revision and order
publication by its history. A delayed ancestor is superseded; a newer reviewed
snapshot can include earlier changes whose publication never succeeded. A retry
of an already accepted intent still returns its original receipt.

This avoids replaying stale per-PR assignments over newer accepted controls and
does not automatically publish a rejected request. The later complete snapshot
is a new explicit, externally authorized request. Its change is computed from
the currently accepted maintained controls, and its full resulting graph is
validated under the agreed admission contract. This cumulative-publication
behavior was not accepted. The revised recommendation in
[the design](../design.md#current-decision-frontier) instead considers one
accepted branch with Selvedge finalizing maintainer commands. The questions below
preserve the alternatives evaluated for the earlier workflow; the
[storage PR note](storage-pr-events.md#remaining-decisions) records the current
decision dependencies.

1. **Meaning of merging a control PR.** Is a normal merge into a control-review
   branch followed by a separate acceptance result acceptable, including a
   merged change that fails publication? Or must the PR remain unmerged until
   its control change is accepted into the registry? This determines the useful
   workflow, not the name of an API endpoint.
2. **Intervening control changes.** Must control publications follow an exact
   accepted control predecessor, stopping later dependent changes after a
   failure, or may independently approved deltas proceed when their reviewed
   assumptions still hold? Neither permits silently applying an older desired
   control value over a newer accepted one.
3. **Only if the PR remains open during finalization:** does the explicit
   externally authorized request authorize its exact immutable change for the
   duration of that attempt, or must a later approval withdrawal/PR closure
   cancel it before acceptance? Native review-branch merge gives an existing
   approval completion event; custom ref installation does not atomically check
   these mutable PR conditions.

Routine implementation details do not require new product decisions: selecting
`updateRefs` versus Git's explicit lease transport, object creation batching,
path/digest serialization, receipt indexing, and precise API error mapping can
be resolved against the already required equality, integrity, and recovery
guarantees. Branch names and whether CI is invoked from one job or a dispatch
are likewise ordinary choices once the authority and workflow contracts hold.

## Verification still required

Before claiming a chosen workflow works on the actual host, exercise its real
credentials and rules in a suitable test repository: successful and rejected
conditional writes; concurrent head advancement; stale or changed PR inputs;
native and constructed merges under the selected review/signature rules;
response-loss reconciliation; and exact receipt/input/output retrieval. If the
constructed-parent option is selected, also verify indirect PR recognition and
ensure proposal ancestry is not mistaken for accepted history. Test publication
failure followed by explicit retry and intervening control changes.

These are unperformed integration checks, not findings that GitHub violates its
documented contract. No remote configuration or approvals were changed. No
host-specific compatibility claim beyond the cited API documentation is made.
