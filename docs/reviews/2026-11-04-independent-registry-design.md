# Independent first-principles registry assessment

Status: revised recommendation, 2026-11-04; analysis only. Available PostgreSQL,
excluded hosted subscriptions and the user's simplicity requirement replace this
review's earlier Git preference. The [accepted design](../design.md) remains the
contract baseline; proposed relaxations are identified below.

## Recommendation

Use **one self-hosted application, one shared checker and PostgreSQL**. Expose
three operations: check a proposed contribution, publish it conditionally, and
read an immutable accepted supergraph. Source CI generates SDL and owns review;
the registry assembles and checks the complete graph, records the result, and
serves its exact bytes. Gateway deployment explicitly selects a revision.

Keep the persistent model small: immutable complete accepted revisions, including
receipt fields, plus the current graph head. No separate receipt service, pending
proposal inventory, queue, mandatory object store, Git mirror or release-upload
phase. Git remains where application source and ordinary reviews belong.

PostgreSQL simplifies acceptance, indexed recovery and historical HTTP reads.
Git's hosted-ref protocol and history traversal no longer buy enough here.
CI-only still needs trusted publication and durable serving infrastructure.
Subscription products are excluded.

The material objection is operational: availability, backups, recovery objectives
and database configuration remain unverified. Suitability does not establish
durability or eliminate custom registry maintenance.

## The minimal record and acceptance operation

An accepted revision retains the complete graph configuration and source claims,
exact submitted and generated bytes, public API schema, report, checker identity,
request identity and payload binding. The returned receipt is a view of that
record. Use a unique, non-null graph/request key for accepted intent lookup;
PostgreSQL supplies indexed uniqueness.
[PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

Bind accepted request identity to server-computed payload fingerprints, including
changes and contribution preconditions but excluding the discovered graph head.
An accepted identity with different contents is an integrity error. Do not retain
failed-attempt bindings solely to detect earlier rejected-ID reuse: that stronger
ADR 0011 guarantee is deliberately removed.

Preserve artifacts as bytes, rather than reconstructing SDL from parsed structures
or JSON. PostgreSQL's `bytea` stores byte sequences; application serialization and
retrieval must preserve them. Keep digests for verification. No second artifact
store is required for the demonstrated workload.
[PostgreSQL binary data](https://www.postgresql.org/docs/current/datatype-binary.html).

Publication follows one sequence:

1. Authenticate the caller and authorize result access, then recover an already
   accepted matching request before applying freshness rules. Recovery returns
   the original result, not old state.
2. Capture head `H`, then load only the immutable complete revision it identifies.
   Do not separately read mutable current schemas and routing: that can
   assemble a configuration that never existed.
3. Check scope and submitted contribution preconditions; construct and evaluate
   the entire candidate **outside a database transaction**. No database lock is
   held while composing, invoking tools or fetching external evidence.
4. In one short transaction, insert the complete accepted revision and receipt
   fields and move the graph head only if it still equals `H`. Commit all of
   these changes together; a failed precondition rolls the whole transaction back.
5. On head contention, reload and reevaluate within a bounded request budget.
   Preserve the original requested changes and contribution preconditions.
   A request-identity conflict instead triggers lookup and binding verification.

PostgreSQL transactions provide atomic visibility. Its conditional update behavior
supports checking the expected head even when another updater commits first.
Capturing an immutable revision makes a long read transaction unnecessary; default
read-committed isolation alone would not make several mutable reads coherent.
These are design deductions from the documented primitives, not tested SQL.
[Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html),
[transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

Every accepted transition creates a new revision. Do not rewind the accepted head
to roll back a gateway; gateway selection is separate. This avoids needing a
second generation protocol merely to distinguish repeated head values.

## Contribution and checking

Source PR CI generates SDL and calls `check`. Retain GitHub Actions OIDC with
separate check/publication grants: it already addresses scoped machine authority
without distributing registry write credentials. Trusted pinned tools process
bounded data; submitted build code never executes with publication authority.

Checking replaces only authorized contributions in an identified snapshot. Report
composition/input validity, composed public API compatibility, supplied-operation
results and Federation changes separately. Keep baseline operations fixed across
both schemas. A proposed document deletion cannot erase regression evidence.
Source repository controls own approval and compatibility exceptions.

After merge, CI explicitly calls `publish` with exact bytes. Composition must
succeed; an externally approved breaking change still has a failing compatibility
result rather than acquiring a second unconditional publication gate. Reports
identify the actual submitted bytes: authentication does not prove a post-merge
build matches the earlier PR check or a deployed service.

## Concurrency and recovery without a workflow engine

Use an expected contribution version, captured before CI checks that its source
is still the intended release and preserved across retries. Unrelated contributions
may advance while the registry recomposes against their latest accepted values.
If a participant changed, return a conflict requiring caller resolution; never
silently refresh that participant's precondition or discard it from a batch.
Versions belong in the snapshot; they do not require mutable per-subgraph tables.

This prevents stale requests from overwriting newer accepted contributions. It
**deliberately relaxes ADR 0012's stronger source-history guarantee**: an old
source job that freshly obtains current contribution versions can still publish.
CI owns which source release is intended. Automatic Git ancestry traversal is
not necessary for ordinary lost-update prevention; retain it only if refusing
that particular delayed-job scenario is itself required.

If the commit response is lost, look up the bound request on the authoritative
writer. A matching record returns the original receipt even after later updates.
An absent result on a lagging replica is insufficient. Retry through the same
unique identity so an unresolved competing commit cannot create another
acceptance. If the writer outcome remains unavailable, report uncertainty.

A rejected check/publication names its evaluated baseline and creates no future
work. Explicit caller retry may succeed later. This proposes relaxing ADR 0011's
mandatory reread/recomposition before rejection: snapshot-labelled rejection is
honest without promising freshness at response time. Operational/tool failure
remains distinct from proven invalidity, and contention retries remain bounded.

## Serve the gateway directly

Provide authenticated HTTPS reads, illustratively:

```text
GET /graphs/{graph}/revisions/{revision}
GET /graphs/{graph}/revisions/{revision}/supergraph.graphql
```

Metadata identifies the accepted record and digest; the artifact response returns
its exact retained bytes. Give the gateway graph-scoped read authority through
its platform's workload identity or secret mechanism, independently of publisher
credentials. Deployment pins a revision and digest.

For the existing Apollo JavaScript Gateway, a startup adapter downloads that
revision, bounds and verifies the bytes, then supplies `supergraphSdl` before
readiness. Apollo documents both string and asynchronous manager inputs; the
installed gateway version remains unverified.
[Apollo Gateway interface](https://www.apollographql.com/docs/apollo-server/using-federation/api/apollo-gateway).

| Event | Behavior |
| --- | --- |
| Normal startup | Retrieve selected revision, verify, initialize, then become ready |
| Registry/database outage during startup | Use a verified local/deployment copy of that same revision; otherwise remain unready |
| Registry/database outage after startup | Continue with the in-memory graph; no registry dependency per client operation |
| New revision selected | Initially use ordinary gateway rollout/restart, retaining the old deployment until replacement initialization succeeds |
| Missing, corrupt or unsupported artifact | Refuse that startup/update; preserve the running old deployment and report the cause |
| Historical revision selected | Retrieve its exact bytes; deployment must establish that current subgraphs still support it |

A cache must not substitute a different last-successful revision. Cold starts
through a complete outage require prepositioned selected bytes or another origin;
that stronger availability requirement has not been established. Serving does
not require polling, automatic activation or a gateway replacement.

## Authority, configuration and upgrades

Put contribution grants in trusted, reviewed application configuration; proposals
cannot change their own authority. Authentication and scope checking admit one
bounded attempt under that configuration. Record its identity with acceptance.
Normal configuration deployment may temporarily mix versions, and admitted work
may finish after revocation. This deliberately drops atomic grant/graph admission
and immediate fleet consistency; immediate revocation needs an operational write
stop, not a default distributed cancellation protocol.

Retain artifact-defining routing in accepted graph snapshots. Only an authorized
operator may change it, using the same complete publication transaction. Remove
cumulative control-source/lifetime machinery, maintainer PR tracking and inherited
unpublished control changes. Ordinary operator review and explicit publication
are sufficient.

Release executable checker behavior as trusted, pinned software, recording the
release in each accepted revision. Remove per-graph executable selectors and a
bespoke quiesced-release protocol. Ordinary deployment must support its schema
and application-version compatibility; overlapping trusted checker releases may
produce labelled revisions. Strict monotonic checker adoption is not promised.
Compare new candidates against retained accepted outputs, exposing tool-induced
changes without rewriting history. Unreadable baseline evidence is a failure.

Bootstrap remains explicitly authorized with initial trusted controls and full
validity checks; compatibility is unavailable without a baseline. Ordinary missing
history is an error. Drop the one-SDL-per-source-revision policy: a new intent may
submit different generation of the same source revision. Immutable request binding
establishes accepted bytes; generator determinism is not enforced.

## Weight failures against existing mitigations

These are qualitative judgments; no workload or incident rates were supplied.

| Situation and likely exposure | Existing mitigation and smallest registry response |
| --- | --- |
| Stale jobs: plausible with CI queues/reruns; can restore unwanted SDL | Branch protections establish review; latest-intended-release checks and cancelling superseded builds reduce staleness. Stable contribution preconditions prevent prepared stale writes. Freshly rebased old-source jobs remain possible without ancestry enforcement |
| Ambiguous success: ordinary timeout/crash exposure; replay can overwrite work | Indexed unique request binding and original receipt recovery; CI reruns keep the same identity. This earns its small cost |
| Sustained contention: less likely than occasional overlap without high publication volume; can starve a caller | Bounded retries/backoff and explicit CI reruns. Defer queues or fair scheduling until measured contention warrants them |
| Mixed checker releases: normal rolling-deployment exposure | Pin/test releases and record engine identity. Accept self-consistent output from either trusted release; defer strict release fencing |
| Revocation midrequest: occasional administrative change | Reviewed configuration rollout and bounded attempts. Already admitted work may finish; emergency write suspension remains an operator action. Defer immediate fleet consistency |
| Restore gap: infrequent but high-impact loss of acknowledged evidence | Verified backups/restore and operator reconciliation before replay; neither SQL atomicity nor idempotency repairs missing history |
| Cold-start outage: plausible during coordinated restart or infrastructure failure | Rolling deployment and a verified selected artifact copy preserve availability. Defer redundant origins/HA until the startup availability requirement justifies them |

## Durability and contract changes

Retain accepted records and artifacts without automatic expiry; receipt fields
remain with the record rather than needing their own retention subsystem.
Protect ordinary writes from modifying historical records. Capacity, backup and
restore remain necessary operations.

Verify WAL durability settings and storage behavior before promising durable
acceptance. PostgreSQL documents that disabling `synchronous_commit` can lose
recent acknowledged transactions, while disabling `fsync` can permit corruption.
Local durable commit does not establish zero-loss failover or disaster recovery.
[PostgreSQL WAL settings](https://www.postgresql.org/docs/current/runtime-config-wal.html).
Backups and restoration must be tested; restoring an earlier database can erase
acknowledged receipts. After a known restore gap, reconcile accepted history before
allowing old requests to replay. Missing evidence is not proof of nonacceptance.
[PostgreSQL backup guidance](https://www.postgresql.org/docs/current/backup.html).

This proposes changing ADR 0010's Git/release mechanics to PostgreSQL and direct
HTTP serving, and changing “registry revision” from a Git commit to an immutable
accepted-record identity. Source Git revisions remain separate provenance.
The source-order, rejection-freshness and control/upgrade relaxations above also
need explicit adoption; changing storage alone does not authorize them.
Scoped authority, whole-graph validity, atomic batches, exact retention,
recoverable acceptance and explicit gateway selection remain intact.

## Smallest proof and limits

Use two representative subgraphs and the actual gateway. Check and publish;
race unrelated and same-subgraph contributions; lose a commit response; verify
request identity conflicts and exact historical bytes. Start the gateway over
HTTP, then exercise corrupt artifacts and outages with/without the selected copy.
Restore the database and test an acceptance gap and one checker upgrade.
