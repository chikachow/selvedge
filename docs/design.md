# Federation schema registry design discussion

Status: working design, updated 2026-11-04. This records the handoff and the decisions
reached with grill-with-docs; it is not an implementation specification.
Terminology lives in [the glossary](../GLOSSARY.md).
Accepted ADRs are authoritative for their decisions; the summaries and workflows
below explain their application together. The latest
[independent assessment](reviews/2026-11-04-independent-registry-design.md)
incorporates the user's available PostgreSQL database, rejection of hosted
registry subscriptions, and requirement to justify complexity against real needs
and likely failures. Its architecture and contract revisions are proposals.
The earlier [first-principles reconsideration](reviews/2026-11-01-first-principles-design.md)
records the preceding Git-backed recommendation. The
[system design review](reviews/2026-11-01-system-design.md) records the preceding
assessment within the then-current architecture.

## Requirements carried forward

- Self-host the registry; do not depend on a hosted managed registry subscription.
  The user can provide PostgreSQL. Its operating and recovery arrangements have
  not yet been inspected.
- Keep each mechanism only when it addresses a concrete need. Assess failure
  likelihood, impact, and existing operational mitigations before adding a
  protocol, state model, or dependency.
- Assess generated schema changes on subgraph source PRs before those PRs merge.
  Evaluate the complete proposed federation, including
  coordinated changes to multiple subgraphs.
- Preserve client compatibility with the composed public API, subject to
  repository-authorized exceptions. Successful validation of known operations
  does not establish compatibility for all clients.
- Keep proposed, approved, observed, and active states distinct. Approval alone
  establishes neither deployment readiness nor runtime safety.
- Validate untrusted proposals with trusted tools and policy. A proposal must
  not weaken the rules used to assess itself or gain publication credentials.
- Bound input size, evaluation time, and resource consumption. Treat submitted
  SDL, manifests, operation documents, and provenance as untrusted data; do not
  execute proposal-supplied code with publication privileges.
- Bind results to exact inputs and baseline revisions; account for concurrent
  proposals before accepting their combined configuration.
- Keep Git-host integration outside GraphQL validation logic. Implementation
  requires a separate explicit request.

## First-principles recommendation

Use one self-hosted Selvedge service and PostgreSQL. Share one graph checker
between local use and the service. Source repositories own SDL generation and
review; ordinary operator configuration owns service permissions and maintained
settings. Selvedge provides three complete operations:

| Operation | Result |
| --- | --- |
| Check | Whole-graph diagnostics identifying the submitted bytes and evaluated baseline |
| Publish | A complete accepted revision containing its inputs, generated bytes, report, checker identity and publication receipt |
| Read | Authenticated retrieval of the exact retained supergraph selected by the gateway deployment |

Store the current registry revision and immutable accepted revisions in PostgreSQL.
Receipt identity and payload binding belong to the accepted revision; they need
no separate workflow model. Evaluate outside the write transaction, then retain
the revision and advance the expected head atomically. Concurrent changes require
reconstruction against the new head before another acceptance attempt. The user
selected per-subgraph optimistic-concurrency conditions: unrelated publications
can be retried internally, while a changed participant requires caller resolution.

This removes Git commit construction, registry-write credentials, history scans
for receipts, and mandatory release uploads. No queue, second artifact store,
Git mirror, PR controller, or configurable backend framework has a demonstrated
need. Source Git identities remain provenance; a registry revision would instead
identify an immutable database record. The earlier Git-specific ADR and glossary
wording needs revision when that storage proposal is adopted. The glossary's
registry revision definition now describes the domain record independently of
its storage mechanism.

The [PostgreSQL data core](postgresql-data-core.md) defines the proposed relations,
constraints, database privileges and publication transaction. Its relational
membership model lets PostgreSQL enforce the identity of retained subgraph inputs
as well as atomic publication. It also owns the empty-graph and concurrency
contracts, including the distinction between caller conditions and the registry
revision used for composition.

The [independent assessment](reviews/2026-11-04-independent-registry-design.md)
owns the detailed rationale, gateway failure behavior, and explicit proposals to
relax stronger earlier contracts. Database availability does not settle backups,
restore behavior, or cold-start availability. The accepted sections below record
the prior contractual baseline, not a requirement to implement its Git machinery
alongside PostgreSQL.

## Accepted decisions

- Source-repository automation may submit only its permitted subgraph schemas
  and provenance. Registry maintainers control policy, routing, and ownership
  configuration. Authenticated publication is scoped to those permitted updates.
- Compatibility exceptions belong to source-repository protection rules and
  their authorized bypass users/groups, outside Selvedge's implementation:
  [ADR 0001](adr/0001-repository-managed-compatibility-exceptions.md).
- The first release serves the organization's own operation. Support for
  independent operators is deferred; portability remains desirable.
- Deployment environments have no built-in domain meaning:
  [ADR 0002](adr/0002-no-environment-domain-model.md).
- The release provides bounded static schema assurance:
  [ADR 0003](adr/0003-bounded-static-schema-assurance.md).
- Gateway deployment configuration selects an approved artifact explicitly:
  [ADR 0004](adr/0004-explicit-artifact-activation.md).
- One complete graph directory is the core input; initially one configuration
  occupies each registry repository:
  [ADR 0005](adr/0005-graph-directory-input.md).
- Accepted registry snapshots retain their exact generated outputs and
  publication receipts in Git. Immutable GitHub releases distribute those bytes;
  accepted snapshots, receipts, and published artifacts have no automatic expiry
  or pruning. This replaces the generation/storage direction of ADR 0006:
  [ADR 0010](adr/0010-retain-validated-outputs-with-acceptance.md).
- Source-PR checks are part of the first release:
  [ADR 0007](adr/0007-check-schemas-in-source-prs.md).
- Source PRs own schema approval, and the service directly records authorized
  schema/provenance updates without mirrored registry PRs:
  [ADR 0008](adr/0008-source-prs-own-schema-approval.md).
- Source checks are snapshot-scoped. Publication recomposes against the latest
  registry and handles independent concurrent updates through internal retry:
  [ADR 0009](adr/0009-snapshot-checks-and-conditional-registry-updates.md).
- Stable request identities and durable receipts recover original acceptance;
  rejected requests require caller correction or explicit retry:
  [ADR 0011](adr/0011-caller-owned-retries-and-publication-receipts.md).
- Source ancestry orders updates to the same subgraph; overtaken revisions do
  not roll back newer state, and coordinated batches are not silently reduced:
  [ADR 0012](adr/0012-order-publications-by-source-history.md).
- Separate maintainer PRs authorize control changes, which use the same trusted
  snapshot finalizer under existing governing controls:
  [ADR 0013](adr/0013-finalize-approved-controls-through-the-shared-publisher.md).
- Initial CI requests use GitHub Actions OIDC with separate scoped check and
  publication grants; outbound GitHub App credentials stay in the service:
  [ADR 0014](adr/0014-authenticate-ci-requests-with-actions-oidc.md).

## Accepted comparison and result contracts

A source check evaluates generated candidate SDL in the complete federation
against an identified registry snapshot. Its report distinguishes the source PR
head, actual source build revision, SDL digest, and registry baseline. It does
not claim that every difference from the registry was introduced exclusively by
that source PR if its target branch has unpublished schema changes.

Where registry PRs are used for maintained configuration, checks compare the
exact registry target with the combined candidate. A separate deployment
comparison reports the net change between explicitly supplied previous and
selected artifacts; it does not discover runtime state or attribute earlier
accepted changes to every subsequent proposal.

Validity and compatibility are distinct checks. Composition, input, and tool
failures fail validity. Public API breaks and newly invalid known operations fail
compatibility, subject to externally configured source-repository bypass.
Dangerous and Federation changes receive notices for ordinary review. An
intentionally accepted breaking change remains a failing compatibility result
in reports. Selvedge does not decide who may approve it or require another
registry exception PR, and publication must not reinstate an unconditional
compatibility-pass requirement. Input validity remains required; composition
is required whenever the configuration has subgraphs. Empty revisions follow
the [data core's explicit unavailable-artifact rules](postgresql-data-core.md#empty-graphs).

When a proposal changes a supplied operation corpus, the baseline corpus remains
fixed while checked against both schemas. Proposed corpus changes are assessed
separately, including additions, modifications, and removals. Deleting a document
cannot erase the regression evidence from the baseline comparison.

## Accepted evidence and bootstrap contracts

The initial provenance guarantee covers authenticated submissions and artifact
derivation from exact accepted registry inputs. Record verified source facts
separately from claimed build provenance; mandatory build attestations are
deferred. A submitted source revision does not by itself prove which schema a
build produced or a deployed binary exposes. Authenticating a request does not
turn its caller-supplied metadata into independently verified evidence.

Creating the first graph requires an explicit bootstrap operation with input
validation and compatibility reported as unavailable. Graphs may initially have
zero subgraphs and may return to that state after removals. Such revisions have
no composed artifact; nonempty revisions require successful composition, as
described in the [data core](postgresql-data-core.md#empty-graphs). An unexpectedly
missing baseline in an ordinary operation remains an error. The initial trusted
configuration must be supplied through an authorized setup path; bootstrap is
not permission for an arbitrary source publisher to establish its own controls.

## Architectural direction

Prefer one Rust codebase exposing a portable checker CLI and the request-driven
service already justified by authenticated submission, trusted reporting, and
publication. Share complete operations across callers; do not require each
source workflow or maintainer integration to implement snapshot assembly,
contention handling, or acceptance recovery.

The recommended ownership split is:

| Module or adapter | Owns | Its caller need not implement |
| --- | --- | --- |
| Graph checker | Complete, explicit baseline/candidate graph inputs; composition; public API comparison; operation validation; Federation review output; generated files and structured report | Engine-specific calls, diagnostic mapping, or separate interpretations of validity and compatibility |
| Registry publication module | Accepted snapshot loading; permitted proposal assembly for checks; publication intent binding; current scope and source-order checks; conditional acceptance; receipt recovery; exact accepted-output retrieval | Git concurrency, stale candidate reconstruction, receipt-history traversal, or the input/output acceptance protocol |
| GitHub adapter and submission client | Incoming OIDC validation; immutable request capture; verified check-target association; GitHub reporting, source evidence, hosted writes, and release transport | GitHub authentication and request/response mechanics in the graph checker |

These are responsibility boundaries, not a requirement for separate deployed
services, generic provider interfaces, or a framework of interchangeable
backends. The GitHub adapter performs host operations for the publication module;
it does not contain a second acceptance algorithm. Source CI owns SDL generation,
invocation, and explicit retry; a thin submission client can handle authentication
and protocol details without imposing a new centrally approved build workflow.

The illustrative caller operations are:

```text
check(proposal, identifiedBaseline) -> report
publish(publicationIntent) -> publicationOutcome
readAccepted(registryRevision) -> retainedArtifactBundle
```

The local CLI invokes the same graph checker with complete graph directories.
A deployment comparison supplies both previous and selected artifact inputs
explicitly. These are capabilities, not a commitment to three HTTP endpoints:
accepted-artifact retrieval may use Git through a CLI. Method names and wire
formats are implementation choices; the important interface includes the result
meanings and recovery guarantees below.
Preparing, validating, and installing a candidate remain internal steps of
publication. A prepared candidate or successful check is never publication
authority, and does not create a durable draft or promise eventual acceptance.

Keep Apollo composition and GraphQL Inspector behind narrow, demonstrated
integration seams. Exact dependencies, versions, licences, and the direct Rust
composition entry point still need verification against representative schemas
and the actual gateway. A preference for Rust does not justify implementing a
new composition engine or compatibility classifier. Choose work storage from
any agreed recovery guarantees; measure execution or lookup costs before adding
worker services or caches. A durable candidate inventory needs its own
demonstrated caller requirement.

The handoff's reference gateway uses introspection; the agreed direction supplies
a precomposed artifact. No concrete gateway or subgraph repositories are available
yet, so source CI and merge-triggered deployment behavior are design choices,
not observed behavior. The artifact governs the gateway's execution
configuration; deployed subgraphs must still support it. Static schema analysis
does not establish equivalent resolver, authorization, or performance behavior.

The initial release has no deployment orchestrator, automatic operation
collection, runtime drift service, environment hierarchy, or multi-host plugin
system. Those concerns are outside the agreed release. No concrete source
repositories or deployed versions have been inspected, so latency, bundle size,
contention, and history-lookup costs remain unmeasured.

## Input and trust ownership

Authentication establishes caller context at the incoming boundary. The
publication module then applies the accepted graph's grants to the parsed
operation and every submitted participant. On reconstruction after contention,
recheck scope under the newly accepted controls as well as source ordering.
Proposed ownership or policy cannot authorize its own admission.

Capture the received bytes and verified context once for an attempt; compute
their digests internally and use that same immutable materialization through
checking and acceptance. Preserve verified context separately from the caller's
source/build claims. A type name, supplied digest, mutable path, PR number, or
claimed approval flag does not establish those guarantees. Source checks may
write their associated GitHub reports but cannot mutate the accepted registry.

The checker consumes trusted, pinned tools and treats proposed inputs as data.
An external helper must not inherit publication credentials or execute arbitrary
commands supplied by proposal fields. The concrete execution arrangement and
budgets remain implementation work; a separate sandbox service is not assumed. Toolchain
changes still use the existing-control admission and separate proposed-control
evaluation required by ADR 0013.

## Accepted service and source workflow

The source PR itself is the proposal. Candidate checks are separate from registry
mutation, and ordinary schema changes do not create a second review object.

1. Source CI generates SDL from an identified source PR build revision.
2. The service authenticates the request, checks permitted subgraph scope, and
   evaluates the complete candidate against an identified registry snapshot.
   Results attach to the source PR; checking creates no registry branch or PR.
3. Source repository controls decide whether the PR may merge, including who
   may bypass compatibility checks. Those approval policies are configured and
   enforced outside Selvedge.
4. After source merge, trusted CI explicitly requests subgraph publication for
   an identified source revision and SDL digest. The shared publication lifecycle
   below applies the permitted schema/provenance replacements and returns the
   acceptance result. Mere overlap of independent valid publications is not a
   semantic conflict.
5. Immutable release publication distributes the accepted bytes without
   recomposition. Explicit gateway selection remains separate. Policy, routing,
   and ownership configuration remain under registry-maintainer control, and
   their input-changing updates must preserve the same complete-snapshot
   guarantee.

The service authenticates and scopes publication authority. It does not inspect
reviewer membership to grant exceptions, synthesize approvals, or require an
exception PR in another repository. A publication request's relationship to the
previously checked inputs needs an explicit contract; this is input integrity
and freshness, not an application approval policy.

An unsuccessful publication belongs to its source revision/pipeline. Rejected
requests do not become background publication work. Source ordering and retained
receipts prevent delayed requests from restoring obsolete state. Coordinated
multi-subgraph changes remain checkable and publishable as one complete batch,
with authority for every participant and no silently discarded updates.

Validation still uses the portable checker. Source submission is request-driven:
source CI calls it explicitly, waits for a result, and owns scheduling and
retries. Direct execution of the shared checker can avoid dispatch and
background-job state, subject to bounded execution and implementation validation.
Storage PR event intake remains a separate, unaccepted Q27 proposal; it must not
silently extend source submissions into background publication work.

## Shared publication lifecycle

Source batches, authorized maintainer changes, and explicit bootstrap have
different admission and input rules but share the acceptance operation. A generic
change payload must not erase those distinctions or confer authority over other
paths. The concrete admission mechanism for maintainer PRs remains open.

1. Validate the request and stable intent binding. Establish the caller's right
   to access the result; recover any original accepted receipt before replay or
   an obsolete-source decision. A reused identity with changed inputs is an
   integrity failure.
2. Load accepted head `H`, its full inputs, and governing controls. Check the
   current requested scope, all source participants, and applicable control
   preconditions. Ordinary missing baselines are errors; only explicit authorized
   bootstrap may create the first accepted graph.
3. Apply only the authorized changes to `H`. Preserve unrelated current inputs
   and the entire submitted batch. Source-history advancement with unchanged
   SDL still records progress; textual merging of generated SDL is not a
   substitute for the submitted schema replacement.
4. Invoke the shared checker on that complete candidate, retaining its outputs
   and reports. Existing controls govern admission of control changes; proposed
   controls receive their separate evaluation. Compatibility failures remain
   visible and do not become an unconditional publication prohibition.
5. Construct the complete snapshot and receipt and install it only if the
   accepted ref still equals `H`. If it moved, repeat from current accepted
   state, including receipt lookup, scope, ordering, and full evaluation. Reuse
   computed results only when all their consumed inputs still match.
6. Before reporting semantic rejection, read the accepted head again. Reevaluate
   if it changed during evaluation; if that read is unavailable, report an
   operational failure. A rejection identifies its evaluated snapshot and does
   not promise continued invalidity after the final observation. Bound contention
   work and distinguish exhaustion from invalid composition. Reconcile an
   uncertain write before replaying it or claiming acceptance did not happen.

The return value exposes the distinctions callers need:

| Outcome | Meaning and next action |
| --- | --- |
| Accepted, including recovered acceptance | Return the original receipt and registry revision; a retry never restores that old snapshot over newer accepted work |
| Validity rejection | Identify the evaluated revision and diagnostics; accepted state is unchanged, and correction or explicit retry belongs to the caller |
| Superseded source or conflicting control assumptions | Do not silently drop participants or substitute a different change; return the relevant evidence for resolution |
| Authorization or integrity failure | The request cannot proceed as supplied; changing transport identity does not authorize changed contents |
| Unavailable evidence, tool/infrastructure failure, or exhausted contention | Report the actual operational failure, not a semantic schema conflict or missing-evidence pass |
| Unverified acceptance | A write may have happened; preserve the recovery identity and reconcile before another acceptance attempt |

These are outcome categories, not a committed API enum. Missing ancestry is
unavailable evidence, not proof of divergent history. A source check's validity
failure can include inability to execute the tool, while publication still
distinguishes that operational cause from a proven composition rejection.

Release distribution follows accepted evidence. Copy the selected retained
bytes without recomposition and report release availability separately from
registry acceptance. An upload failure does not turn an accepted publication
into a rejection. Retrieval verifies acceptance and artifact identity; gateway
deployment explicitly selects the result and remains responsible for subgraph
readiness and rollback feasibility.
The source publication caller owns explicit retry of failed distribution from
the accepted receipt; that retry copies recorded bytes rather than submitting a
new schema update. The storage-PR integration must expose equivalent completion
and retry behavior through its chosen caller surface under Q27.

If Q27 adopts event-driven commands, receipt of a webhook is not registry
acceptance. That adapter needs durable intake/reconciliation and a way to keep
terminal rejections from being retried merely because an old command is
rediscovered. Successful Git receipts alone do not record rejected attempts.
This is a concrete added lifecycle cost, not justification for a general-purpose
workflow engine or an assumed database.

## Accepted Git snapshot direction

Q25 accepts self-contained registry snapshots under
[ADR 0010](adr/0010-retain-validated-outputs-with-acceptance.md), superseding
ADR 0006. The generated output used for validation is retained at acceptance;
release distribution does not regenerate it. Every accepted input-changing
writer, including maintainer configuration workflows, must preserve that
guarantee.

Use Git's native content relations and one designated accepted sequence. If an
accepted merge has proposal parents, those proposal ancestors are not themselves
accepted snapshots; retrieval and receipt lookup follow the designated acceptance
sequence, such as its first-parent history. Composition content, directional
comparison inputs, publication intent, registry acceptance, and generated-byte
identity have different purposes and must not be collapsed into one identifier.
Composition identity includes the exact tools and consumed configuration;
comparison identity additionally includes its ordered baseline/candidate,
policy, and operation inputs. This is what permits reuse without confusing equal
SDL with equal evaluation or equal source progress.

Exact manifests, receipt lookup, and hosted ref operations are implementation
design work. Start with retained accepted history and add indexes or caches only
for demonstrated lookup or execution costs. Managed candidate branches would
add ownership, supersession, retention, and cleanup obligations without a current
durable-drafting requirement. See the
[comparison, failure analysis, and local experiment](research/git-state-model.md).

## Current decision frontier

Self-hosting without a hosted registry subscription is required, and PostgreSQL
can be supplied. The latest assessment therefore recommends PostgreSQL as the
sole accepted record, with direct authenticated artifact reads. The preceding
Git workflows remain historical alternatives, not additional systems to build.

The simplicity review proposes deliberate changes to stronger earlier contracts:

- **Storage:** replace Git registry revisions and mandatory release uploads with
  immutable database revisions. Retain exact inputs, outputs, accepted-request
  recovery and no automatic expiry. Update the Git-specific wording in ADRs 0005
  and 0010 and the glossary when adopting the replacement.
- **Source ordering:** fixed expected-subgraph revision preconditions plus a CI
  check of the intended source revision replace mandatory ancestry enforcement.
  Capture preconditions before that CI guard and keep them fixed across retries.
  Unrelated subgraph updates can be retried internally; an intervening update to
  the same contribution requires a fresh intentional request. This addresses
  common out-of-order jobs but relinquishes ADR 0012's registry-enforced ancestry
  guarantee for publishers that do not follow the CI contract.
- **Configuration and releases:** ordinary reviewed operator configuration and
  trusted application releases replace cumulative control-source publication,
  per-graph executable selection and mandatory single-version write cutover.
  Retain artifact-defining configuration and checker identity with every
  accepted revision. This changes ADR 0013's atomic admission and upgrade
  semantics; bounded in-flight work and intentionally overlapping trusted
  releases are allowed unless a specific transition requires stronger handling.
- **Retry scope:** accepted revision identity and payload binding provide the
  receipt. Do not retain rejected-attempt state solely to police failed request
  ID reuse. An identified composition failure can return without rereading the
  graph head; a caller can retry if later graph changes could make it valid.
  These choices narrow ADR 0011's stronger identity/freshness behavior without
  changing atomic acceptance or recovery of a successful publication.
- **Generation:** bind each accepted intent to its exact bytes and provenance.
  Do not introduce an additional one-SDL-per-source-revision restriction without
  evidence that producers need it. Fresh publication checks do not claim that
  an earlier PR check covered different post-merge output.

These are explicit recommendations for adoption, not claims that weaker
mechanisms preserve every earlier guarantee. The
[independent assessment](reviews/2026-11-04-independent-registry-design.md)
explains the concrete failures, their likely relevance, cheaper mitigations and
remaining limits. No application implementation is authorized by this analysis.

The next useful evidence is a small end-to-end path using actual subgraph schemas,
source CI identities and the installed gateway. Verify scoped contribution,
concurrent publication, recovery after a lost success response, exact historical
HTTP retrieval and gateway startup during an outage. Exercise PostgreSQL commit,
rollback and restore behavior directly; local Git experiments do not verify the
new storage proposal. Confirm deployment and database operating arrangements,
including acceptable restore loss and startup availability, before adding more
infrastructure to address them.
